chapter 02 the shape of all software

Software has two halves.

One half you can see and touch. One half you cannot reach. Everything else in this lesson is a detail of that split.

you can see it

The frontend

Runs on the device in your hand. Draws pixels, catches taps, plays animations. It is a very convincing menu — and nothing more.

you never see it

The backend

Runs on a machine far away that you do not control. Holds the rules, the secrets and the truth. Decides what is actually allowed to happen.

the mental model keep this one picture

Dining areafrontend — where you sit
Kitchenbackend — where the work happens
Pantrydatabase — where things are kept

You order from a menu. A waiter carries the order through a door. Food comes back. You never see the fridge.

Remember

Frontend and backend are not two parts of one program. They are two separate programs, running on two different computers, talking over a network.

chapter 03 front of house

Frontend is presentation.

Its whole job is to turn data into something a human can look at, and turn a human's finger into a piece of data.

It runs on your device

Phone, laptop, TV, watch. Downloaded to you, then executed by you.

It only knows what it was sent

A frontend showing a price knows that price because a backend told it. It is repeating, not deciding.

Beginner mistake

Believing the frontend is "the app". If your phone is switched off, the app still exists — the half that matters is still running.

chapter 04 back of house

Backend is the trusted worker.

It is the hidden half: logic, rules, security checks, and the wiring that talks to storage. Watch a single tap travel all the way down.

the journey

Usertaps something
Internetthe wire in between
Serverruns the backend program
Databasekeeps it after everyone leaves

Applies the rules

"Is this coupon still valid?" "Has this worker already been deducted this month?" Rules live here because here cannot be edited by the user.

Guards the secrets

Password hashes, payment keys, other companies' API keys. None of it is ever shipped to a device.

Holds the shared truth

One value that everybody reads: the stock count, the balance, the ride status.

Interview tip

Asked "what is the backend?", do not say "the database and the API". Say: the trusted half of the application — logic, rules, authentication and data access — running as a process on a machine the user does not control.

Beginner mistake 1

"Backend = database." The database is one piece. The backend is also the logic, the rules, the security checks and the way it talks to clients.

Beginner mistake 2

"Server = backend." The server is the computer. The backend is the software running on it. One server can run several backends; one backend can spread across many servers.

A stale process still holding a port will break a perfectly healthy application. That is the clearest proof that "server" and "backend" are different words.

The part that trips people up

Your backend is a server to the browser and a client to the database — in the same request. The role depends on who is asking whom, not on what the machine is.

Beginner mistake 4

Assuming the two halves are one program sharing memory. They are separate programs on separate machines, so every message costs time and can be lost in transit.

A request is a question. A response is an answer. Both are just text.

HTTP

The agreed format for asking and answering. A method (GET, POST), an address, headers, and a body.

JSON

The agreed shape of the data inside. Plain text that both halves understand, even though they are written in different languages.

API

The published list of questions this backend accepts. A contract: break it, and every old app version breaks with it.

chapter 08 beginner mistake 1, in detail

The pantry is not the cook.

A request passes through four layers. Only the last one is the database — and it is the only layer with no opinion about your business.

Controllerowns the HTTP surface
Serviceowns the rules
Repositoryowns data access
Databaseowns storage only

who decides what

"Is this deduction allowed twice?"service layer — a business rule
"Store this number in this row."database — no judgement applied
Why this matters

If a rule only exists in your code and you forget to run it, the database will happily store the wrong thing. It never says no on your behalf unless you gave it a constraint.

chapter 09 advantages of the split

Four things one device can never do alone.

Each card is a problem that disappears the moment you add a backend.

sharing

Shared state

My phone cannot hold the data your phone needs to read. A backend gives everyone one copy to look at.

trust

Trusted enforcement

My phone cannot be trusted to decide my own salary, my own discount, or whether my password was right.

power

Work devices can't do

Heavy computation, secret API keys, scheduled jobs that run at 2am while every phone is asleep.

reach

Many faces, one brain

Web, Android, iOS and an internal tool can all call the same backend. Write the rule once, honour it everywhere.

Interview tip

The strongest one-line answer: a backend exists because some state must be shared between users, and some decisions must be made where the user cannot reach them.

chapter 10 beginner mistake 3 — the expensive one

Never trust the frontend.

You shipped that code to the user's machine, so the user owns it. Everything arriving from a client is a claim, never a fact. Try breaking this checkout.

Waiting for an order.
what the server does with it
Turn the switch on, set the total to 0, and place the order. Then turn it off and try again.

Passwords

A client cannot check a password, because it would need the correct value to compare against — you would be shipping the secret to the attacker.

Hidden buttons

A greyed-out button is not security. The endpoint behind it is still reachable by anyone who skips your interface entirely.

Tokens

A token's payload is encoded, not encrypted — anyone can read and edit it. Only the signature makes it trustworthy, and only your server can check that.

Beginner mistake 3

Anything on the user's device can be inspected and changed by the user. Never let the frontend decide whether a password is correct, and never hardcode a secret key into an app.

chapter 11 where the rules live

"Only 2 left in stock."

The true count lives in exactly one row, in one database. Each phone holds a stale photocopy. Here is what happens when two shoppers act at the same instant.

Shopper Asees: —
Shopper Bsees: —
true stock in the database 2
timeline
t1 · shopper aReads the stockgets 2
t2 · shopper bReads the stockalso gets 2
t3 · shopper aWrites 2 − 1 = 1stock becomes 1
t4 · shopper bWrites 2 − 1 = 1stock is still 1
resultTwo sold. Count dropped by one.One unit sold that does not exist.

the broken shape

read → decide → writea gap where someone else can slip in

Checking harder in your application code does not fix this. The gap is the problem, not the check.

the fix one atomic step

read and write togetherthe database refuses if the condition fails

A condition on the update, a row lock inside a transaction, or a uniqueness rule on the table. The last one survives a future developer forgetting the check.

Remember

Business logic belongs on the server not because the server is faster, but because the server is the only place where the rule cannot be edited by the person it applies to.

chapter 14 the five traps

Beginner mistakes, collected.

Each of these feels reasonable until it costs you an outage.

Mistake 01 — backend equals database

The database is just one piece. The backend also includes the logic, the rules, the security checks, and the way it talks to clients.

Mistake 02 — server equals backend

The server is the computer. The backend is the software running on that computer. The words are used loosely, but the distinction matters the day a stale process holds your port.

Mistake 03 — trusting the frontend for security

Anything on the user's device can be inspected and changed by the user. Never let the frontend decide a password is correct, and never hardcode a secret key into the app.

Mistake 04 — assuming they are one program

They are two separate programs that talk to each other over the internet. Every message costs time, and any message can be lost.

Mistake 05 — thinking backend is only writing code

It also means storing data, deploying to servers, and staying reachable over a network. An expired certificate takes a service down without a single line of code being wrong.

chapter 15 what the split costs you

The wall is not free.

Splitting an app in two buys safety and sharing. It charges you in latency, uncertainty and operational work.

Latency is real

Every rule enforced on the server costs a round trip. That is why apps show an optimistic result first and correct it later.

Failure can be partial

Your write may have succeeded while only the reply was lost. The client cannot tell the difference, so it retries.

The contract is forever

Old app versions keep calling your API for years. You can add to a response; you cannot quietly remove from it.

Someone must run it

Deploys, migrations, certificates, backups, monitoring, capacity. None of this is code, all of it can take you offline.

the consequence nobody warns you about

Reply gets lostclient has no idea

so it retries

Same write arrives twiceit must be safe to repeat

This is why serious write endpoints carry an idempotency key, and why a duplicate guard that never actually persists its flag is a real bug rather than a tidy detail.

chapter 21 take this with you

The whole lesson, on one card.

frontend

Runs on the user's device. Draws, collects input, renders answers. Never decides anything that matters.

backend

The trusted half: logic, rules, security checks, data access. A process on a machine you control.

server

The computer. Not the same word as backend. One server can run many; one backend can span many.

client

Whoever asks. A role in a conversation, not a kind of hardware.

database

Storage with no opinion. It enforces only the constraints you gave it.

request

The client's question. Method, address, headers, body.

response

The server's answer. Status code plus body.

api

The published set of questions a backend accepts. A contract you cannot quietly break.

trust rule

Client input is a claim, never a fact. Re-verify, re-compute, re-authorise on the server. Every time.

the model

Frontend is the dining area. Backend is the kitchen. Database is the pantry.

The test that settles every argument

For each job you listed, ask: would this still be correct if the user hacked their own copy of the app? Anything that fails that question belongs on the server.
