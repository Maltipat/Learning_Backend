?the question nobody answered yet

A request and a response are messages. But what is actually written inside them?

What you learned so far

A request has a method, an address, headers and a body. A response has a status code, headers and a body.

What was left vague

The body. Every diagram said "the data goes here" and moved on. This lesson opens that box.

the answer, in one line

Most of the time, the body is written in JSON — a plain-text way of writing down data that both sides agree how to read. That is the entire subject of this lesson, and we will not assume you have ever seen it.

03the name, decoded

What is JSON?

The full form is JavaScript Object Notation. Three words, and the third one is the important one.

Notation the key word

A notation is an agreed way of writing something down. Sheet music is a notation. A recipe is a notation. It is not a machine or a program — it is a convention about marks on a page.

Object a thing with details

In everyday terms: one thing described by several labelled details. A person has a name, an age, an email. That bundle is an object.

JavaScript only history

The way of writing was borrowed from a programming language called JavaScript in the early 2000s. That is all that word means here — it is a historical fact, not a requirement.

so, plainly

JSON is an agreed way of writing data as plain text, so that any program can write it and any other program can read it back and get the same meaning.

What JSON is

A data format

A set of rules for writing data down. That is the whole of it. Nothing more.

Plain text

Ordinary characters you could type on any keyboard. You can open JSON in a notepad and read it.

A shared agreement

Its power is that everybody agreed on the same rules. That is the only reason it is useful.

What JSON is not

Not a programming language

You cannot write instructions in it. It has no commands, no loops, no decisions. It only describes data sitting still.

Not a database

It stores nothing on its own. A database keeps data safe over time; JSON is just how data might be written while travelling.

Not an API

An API is the set of requests a server accepts. JSON is what those requests and replies are often written in. Different layers entirely.

Not a backend technology

It is not something you install or run. There is no "JSON server". It is a way of writing, like handwriting versus print.

whywhy it was created, and why it won

The problem in the early 2000s

Web pages needed to fetch small pieces of data from a server without reloading. The existing format was heavy and awkward to work with, and everybody wanted something smaller.

Discovered, then written down

Douglas Crockford described and popularised JSON around 2001, using a way of writing objects that JavaScript already understood. It was standardised properly later — first as a specification in 2006, then as an international standard.

Why humans like it

The labels are written out in full, one thing per line, with indentation showing what belongs inside what. You can read it aloud without being taught.

Why machines like it

The rules are tiny and completely unambiguous. Only six kinds of value exist, punctuation is fixed, and there is exactly one correct way to read any valid document.

Why backends use it

A Java server and a Python script and an iPhone app all need to agree. JSON belongs to none of them, so all of them can use it.

06one thing, described

  
The JSON object

  
Before the JSON meaning, the everyday meaning. An object is simply one thing, described by a set of labelled details.


  

    

      
A passport is an object
One thing. Its details are labelled: surname, given name, date of birth, number. Each label has one value.

      
A product tag is an object
One thing. Labels: name, size, colour, price. You read the label to know what the value means.

      
A person is an object
One thing. Labels: name, age, email. Exactly what we are about to write down.

    

    

      

      
in JSON
An object is written between curly braces. Inside, each labelled detail is a label, a colon, and a value. That is the entire definition — there is nothing else to an object.

the difference that catches everyone
26 is a number. "26" is text that happens to contain digits. They look almost identical and behave completely differently — you can do arithmetic with the first and not the second. 09a list, in order

  
JSON arrays

  
An array is a list. Where an object describes one thing with labels, an array holds several things in a definite order — and instead of labels, each item has a position.


  

    

      

        

          three skills, in order
          
        

        

          
 an array of strings0 items


[ ]

        

        

          
Square brackets [ ]
These mean "a list". Curly braces mean one labelled thing; square brackets mean several things in a row.

          
Commas between items
Same rule as objects: a comma after every item except the last one.

          
Order is part of the meaning
An array remembers its order. The first item stays first. Positions are counted from 0, so "Java" is item 0 — which surprises everybody once and then never again.

        

      

      

        
≠object versus array — the one thing to keep straight

        

          
Object { }
One thing, several labelled details. You reach a value by its label.
{ "name": "Malti" }

          
Array [ ]
Several things, in order. You reach an item by its position.
[ "Java", "SQL" ]

        

        

          

          
how to choose
Ask: am I describing one thing, or listing many? One user is an object. A page of users is an array of objects. That single question answers it every time.

13three different words, three different jobs

  
JSON and REST

  
This is the single most important distinction in the lesson. HTTP, REST and JSON are constantly said in the same breath, and they are three completely separate things operating at three different levels.


  

    

      

        
HTTP — a communication protocolhow it travels

        
The rules for actually moving a message between two computers: how to open a connection, how to format the lines, what a status code means. It is the road and the traffic law.

      

      

        
REST — an architectural stylehow it is arranged

        
A set of agreed design habits for your API: nouns in the URL, verbs in the method, one resource per address. It is the town planning, not the road.

      

      

        
JSON — a data formathow the contents are written

        
A way of writing the data down inside the body. It is the language the letter is written in — and the road does not care, and the town planning does not care.

      

    

    

      

      
proof that they are separate
You can build a REST API over HTTP that returns XML instead of JSON. You can send JSON over a protocol that is not HTTP. You can use HTTP and JSON while ignoring REST completely. All three combinations exist in the real world — which could not be true if they were the same thing.

    

  


  

    

      
GET /usersa list comes back

      

        
response bodyan array



      

      
Asking for a collection gives you an [ ] array, because many things are coming back. Each item is one { } object.

    

    

      
POST /usersyou send one thing

      

        
request bodyan object



      

      
Creating one thing sends one { } object, because you are describing a single item. No array — there is only one of it.

    

  


  

    

    
an analogy that fixes this permanently
HTTP is the postal service. REST is the convention for how you address the envelope. JSON is the language the letter inside is written in. Change any one of the three and the other two carry on working exactly as before.

  







  
14the same format, a different style

  
JSON and GraphQL

  
You met GraphQL in lesson 7, so this is only about the relationship — not a re-teach.


  

    

      
A GraphQL response is JSON

      

        
a graphql replyordinary json



      

      
Nothing new is happening. It is an object with one key called "data", whose value is another object. Every rule from the earlier sections applies unchanged.

    

    

      
What differs, and what does not

      

        
Same: the reply is JSON
Braces, keys, colons, commas — identical rules.

        
Same: the six data types
Nothing extra is added and nothing is taken away.

        
Different: who chose the fields
In GraphQL the client asked for exactly those fields. The format did not change; the decision moved.

        
Different: the wrapper
GraphQL always wraps the result in a "data" key, and puts any problems in a separate "errors" key beside it.

      

      

        

        
the takeaway
JSON is the format underneath both REST and GraphQL. Changing your API style does not change how the data is written down.

      

    

  







  
15and one more place it appears

  
JSON and RPC

  
Lesson 8 covered RPC. The only point here is that it, too, needs a way of writing data down — and JSON is one of the options.


  

    

      
Some RPC systems use JSON

      

        
a json-based rpc callan object



      

      
The function name and its inputs are written as ordinary keys and values. The format is JSON; only the meaning of the keys is set by the RPC convention.

    

    

      
Others use something else entirely

      
Many high-performance RPC systems do not use JSON at all. They use a compact binary format — data written as raw bytes rather than readable characters.

      

        
JSON: readable, larger
You can open it and understand it. It costs more bytes because every label is spelled out in full, every time.

        
Binary: unreadable, smaller
Much faster and smaller on the wire, and completely meaningless to a human eye. Used where speed matters more than convenience.

      

      

        

        
the honest summary
JSON is extremely common but not universal. "Every API uses JSON" is one of the beginner mistakes in section 25, and this is why.

5the five mistakes that cause almost every failure

    

      
Keys without quotes
name: "Rahul"
A bare word is not text. The reader stops at the first letter.

      
Single quotes
"name": 'Rahul'
JSON only recognises double quotes. Single quotes are simply not part of the format.

      
A trailing comma
25, }
A comma promises another item. If none follows, the reader is left waiting.

      
A missing comma
"Rahul" "age"
Two pairs with nothing between them. The reader cannot tell where one ends.

      
Capitalised booleans
"active": True
It must be exactly true or false, all lowercase. True is an unknown word.

      
Comments
// the user's name
JSON has no comments at all. Any attempt to add one breaks the document.

    

  


  

    

    
how to read a JSON error message
Almost every JSON error tells you a position — a line and column, or a character number. The mistake is usually at that spot or just before it. Do not read the whole document looking for the problem; go straight to the position it gave you.

  







  
18from characters to something usable

  
JSON parsing

  
"Parse" is an ordinary English word meaning to read something carefully and work out its structure. You parse a sentence when you work out which word is the verb. A program parses JSON when it works out which part is a key and which is a value.


  

    

      
Before parsing
A long line of characters. The program sees { then " then n — meaningless marks, one after another.

      
The parser
A small piece of software that walks through the characters applying the eight rules, and works out the structure they describe.

      
After parsing
A usable thing in the program's memory. Now it can simply ask "what is the age?" and get 26 back.

19two long words, one simple pair of ideas

  
Serialization and deserialization

  
These two words appear constantly in backend work and sound far harder than they are. They are simply the two directions of the same door.


  

    

      
going out

      
Serialization

      
Turning a usable thing in memory into text that can travel. "Serial" as in "in a line" — the thing is flattened into one line of characters.

      
Everyday version: writing your address on a form. The place exists in the world; you flatten it into words on paper so it can be posted.

    

    

      
coming in

      
Deserialization

      
The reverse: taking the text and rebuilding a usable thing from it. This is parsing plus putting the results into the shape the program wants.

      
Everyday version: reading an address off a form and finding the actual house. The words become a real place again.

Other words for the same thing

      
You will hear "encode", "marshal", "stringify" and "dump" for serialization; and "decode", "unmarshal" and "load" for the reverse. Different traditions, identical idea.

    

      
Parsing versus deserializing

      
Parsing works out the structure. Deserializing usually means parsing and then filling a specific shape the program expects. In casual speech they are used interchangeably.

    

      
Where it goes wrong

      
Not every kind of thing survives the trip. A date, for example, has no JSON type — it must become text, and both sides must agree on the exact format or it will be misread.

21a preview only

  
JSON vs XML — a first look

  
JSON is not the only data format. The main one that came before it is called XML, and you will meet it properly in the next lesson. For now, just see the difference.


  

    

      
json—

      

        
the same one factbraces and labels



      

      
The label appears once, followed by its value.

    

    

      
xml—

      

        
the same one factopening and closing tags


<name>Rahul</name>

      

      
The label appears twice — once to open and once to close.

    

  


  

    
vsthe shortest honest comparison

    

      
JSON tends to be shorter
Labels are written once. For data-heavy replies this adds up to a meaningful difference in size.

      
XML can carry more description
It supports attributes, namespaces and formal schemas for validation — capabilities JSON does not have built in.

      
JSON is the default for new web APIs
Most APIs built in the last fifteen years chose JSON, largely because it is smaller and simpler.

      
XML is far from dead
Banking, government, publishing, office documents and many enterprise systems run on XML and will for a long time.

    

    

      

      
that is deliberately all for now
XML is a whole lesson of its own — tags, attributes, namespaces, schemas — and it is the next one. Everything you should take from this section is: JSON is a data format, not the data format.

27the honest weaknesses

  
Limitations of JSON

  
Six real problems. Every one of them has caused a production incident somewhere, and knowing them is what separates using JSON from understanding it.


  

    

      
limit 01
No comments

      
You cannot leave a note explaining a field. This is genuinely painful for configuration files, where the person editing them next year needs to know what "retryAfter": 30 is measured in.

      

        
what people trybreaks


{
  // how long to wait
  "retryAfter": 30
}

        
the usual workarounda fake field


{
  "_note": "seconds",
  "retryAfter": 30
}

      

      
The workaround is a real field that the program must be told to ignore. It works, and it is not elegant.

    


    

      
limit 02
Only six data types

      
There is no type for a date, a time, money, a very large number, or a duration. All of them must be squeezed into text or numbers, and both sides must agree on the convention without help from the format.

      

        
Dates
"2026-08-13"
Text, by convention. Nothing stops someone writing "13/08/2026" instead — and then it breaks.

        
Money
19.99
A decimal number can be stored imprecisely by computers. Serious systems store money as whole pennies or as text.

        
Very large numbers
9007199254740993
Beyond a certain size, some readers lose the last digits silently. Large ids are often sent as text for exactly this reason.

      

    


    

      
limit 03
It can become deeply nested

      
Nothing limits how deep you can go, so real documents sometimes end up six or seven levels down. Reading such a thing, and reaching a value inside it, becomes genuinely unpleasant — and one missing level in the middle breaks everything below it.

      
too deep to read comfortably6 levels


{ "data": { "user": { "account": { "billing": {
  "address": { "city": "Pune" } } } } }

    


    

      
limit 04
Large documents are expensive

      
Every key is spelled out in full for every single item. In a list of ten thousand products, the word "price" appears ten thousand times. That is real bytes on the wire, real time to read, and real memory to hold — which is precisely why binary formats exist for high-volume traffic.

      

        
1 product · 128 bytes

        
10,000 products · about 1.25 MB — of which roughly a third is repeated key names

      

    


    

      
limit 05
No built-in schema enforcement

      
Valid JSON does not mean correct data. A document can be perfectly valid and still have an age of "twenty-six", a missing email, or a price of -5. The format checks the punctuation, not the meaning — so every serious system needs its own validation on top.

      
valid json, nonsense datapasses every parser


{
  "age": "twenty-six",
  "price": -5,
  "email": "not an email"
}

    


    

      
limit 06
Binary data does not fit naturally

      
An image, a video or a PDF is raw bytes, and JSON only holds text. To put a file inside JSON it must first be converted into a long string of letters — which makes it roughly a third larger and completely unreadable. This is why files are almost always sent separately, with the JSON carrying only a link to them.

      

        
Stuffing the file in
"photo": "iVBORw0KGgoAAAANSUh…"
Works, wasteful, and unreadable. 33% bigger than the file itself.

        
What is normally done
"photoUrl": "https://cdn/p/12.jpg"
The JSON carries an address; the file travels on its own.

      

    

  


  

    

    
none of this makes JSON a bad choice
Every one of these limits is the price of being simple, and simple is why it won. A format with dates, comments, schemas and binary support would be far harder to implement — and would not have spread to every language on earth in a decade.

33one page

  
Cheat sheet

  
Two minutes of revision before an interview or the next lesson.


  

    
json
JavaScript Object Notation — an agreed way of writing data as plain text. A format, not a language, database or API.

    
object { }
One thing described by labelled details. Reached by label.

    
array [ ]
Several things in order. Reached by position, counting from 0.

    
key
The label. Always text, always in double quotes, unique within its object.

    
value
What the label points at. Always one of exactly six types.

    
string
Text in double quotes. "Rahul"

    
number
Digits, no quotes. Whole or decimal, positive or negative. 25

    
boolean
Exactly true or false, lowercase, no quotes.

    
null
Deliberately no value. Lowercase, no quotes. Different from missing or empty.

    
nesting
A value may itself be an object or an array. No depth limit.

    
request
JSON in the body describes what you are sending. Header says Content-Type: application/json.

    
response
JSON in the body describes what came back. Same rules, opposite direction.

    
parsing
Turning JSON text into structure a program can reach into.

    
serialization
Turning a thing in memory into JSON text so it can travel.

    
deserialization
The reverse — rebuilding a usable thing from JSON text.

    
the 8 rules
Double quotes on keys · double quotes on strings · colon between key and value · commas between items · { } for objects · [ ] for arrays · no comments · six types only.

    
no trailing comma
Never a comma after the last item. The single most common mistake there is.

    
json ≠
Not HTTP (the protocol) · not REST (the style) · not an API (the menu) · not a database (storage).

    
valid ≠ correct
JSON checks punctuation, never meaning. An age of "twenty-six" is valid JSON and wrong data.

json

    

    

      
      JSON is one layer in a stack you now know all of.
    

  


  

    

      
JSON is a way of writing, nothing more

      
Not a language, not a database, not an API, not a technology you install. A notation — like sheet music, or a recipe.

    

      
Two containers, four simple values

      
Objects and arrays hold things. Strings, numbers, booleans and null are things. Every JSON document ever written is those six, arranged.

    

      
Text for travelling, structure for working

      
Serialize to leave, deserialize to arrive. The information never changes — only the form it is held in.

    

      
Valid is not the same as correct

      
The format only checks the punctuation. Whether the data makes sense is entirely your job, and always will be.

  


  

    
♦memory tricks

    

      
Curly for one, square for many
{ } describes one thing. [ ] lists several. That single distinction answers most beginner questions.

      
The colon means "is"
Read "age": 26 aloud as "the age is twenty-six", and JSON stops looking like code.

      
Quotes mean letters, no quotes mean maths
"26" is characters. 26 is a quantity. You can only add up the second one.

      
A comma promises another
Every comma says "something else is coming". A trailing comma is a promise you then break.

      
Notation, not machine
The N in JSON is the whole answer to "is JSON a database?".

      
Post, road, letter
HTTP is the post. REST is how you address it. JSON is the language the letter is written in.

    

  


  

    
keythree takeaways to keep

    

      

        
one
JSON's value is not cleverness — it is agreement. Its rules are small enough that every language implemented them correctly, and that is the entire reason it works everywhere.

      

        
two
Learn to read the punctuation outwards. The outermost bracket tells you whether you are holding one thing or a list, and everything else follows from there.

      

        
three
Keep JSON separate in your head from HTTP, REST, APIs and databases. Being able to say precisely which layer each one lives at is worth more in an interview than memorising the syntax.
