REST APIs

REpresentational State Transfer

A frightening name for a simple idea. REST is not a program you install or a language you learn — it is a set of agreed habits for building an API, so that anyone who has used one API can immediately guess how yours works. This lesson starts from the word itself and ends with you designing endpoints of your own.

03the name, decoded

What is REST?

Before anything else, two words that need defining, because the usual explanations assume you already know them.

Architecture a shape

In building, architecture means the overall shape and arrangement of a structure — not the bricks. In software it means the same: how the pieces are arranged, not which language they are written in.

Architectural style a set of habits

A style is a set of rules a design chooses to follow. Not a product, not a library, nothing to download. If your API follows the rules, it is RESTful. If it does not, it is not. That is the whole test.

So, plainly

REST is a set of agreed rules for designing an API on top of the web, so that every API built that way behaves in a familiar, predictable manner.

The three words in the name

Click each one. The name looks intimidating and turns out to be a plain description of what happens.

word 1 of 3

Representational

You never receive the actual thing stored on the server. You receive a representation of it — a description, written in a format like JSON.

analogy

A photograph of a house is not the house. It tells you enough about the house to be useful.

what that looks like

The real user is rows in a database, spread across tables, with fields you are not allowed to see. What you get is a tidy description of the parts that concern you.

Why was REST created?

The web already worked

By the late 1990s the web was carrying enormous traffic without collapsing. Somebody asked the useful question: why does this scale so well?

It was described, not invented

In 2000 Roy Fielding wrote a doctoral thesis naming the properties that made the web work, and called that set of properties REST.

Then it was borrowed

Engineers realised those same properties would make their own APIs scale. So they started designing APIs the way the web was already built.

Worth remembering

REST did not invent anything new. It is a description of habits that were already proven to work at the scale of the entire internet.

Why did it become so popular?

Nothing new to install

It uses HTTP, which every device, language and network already speaks. No special tooling, no licence, no library.

You can read it

GET /users/10 needs no documentation to guess. Earlier styles produced messages nobody could read by eye.

It is easy to test

Any browser, any command line, any phone can send a REST request. You can poke a REST API with tools you already have.

It transfers between jobs

Learn REST once and every REST API in the world is partly familiar. That predictability is the entire product.

What REST is not

Not a language. Not a library. Not a protocol. Not the same thing as HTTP, and not the same thing as an API. It is a set of design rules — and section 16 comes back to each of those confusions properly.

04life before the agreement

Why do we need REST?

Here are four APIs from four teams, all doing exactly the same thing: fetching user number 10. Press the button and watch what a developer has to deal with.

With REST

Press the button to see what it takes to talk to all four.

Without a standard

Every API is a new language. You read documentation for days, and none of what you learn helps you with the next one.

Tools cannot help you

If nobody agrees where the id goes or what a success looks like, no tool can generate code, cache answers, or retry safely for you.

With a standard

One shape, learned once. New API, same guesses. Tools, caches and error handling all work without being told anything.

The point of standardisation

A standard does not make any single API better. It makes every API cheaper to learn, because the knowledge carries over. That is why REST spread — not because it was clever, but because it was predictable.

PUT versus PATCH, the difference that matters

PUT replaces the entire thing with what you sent — any field you leave out is wiped. PATCH changes only the fields you sent and leaves the rest alone. Run both above on the same product and watch what happens to the fields you did not mention.

08the noun at the centre

The REST resource concept

This is the single idea that makes REST click. Everything a REST API exposes is a thing, not an action.

A resource is any thing your system has that a client might want — and it is always named with a noun.

It is a noun never a verb

A user. A product. An order. Not "getUser", not "createOrder" — those are actions, and actions are the method's job.

It has an address a url

Every resource can be reached at a path. If you cannot write its address, it is not a resource yet.

It comes in two shapes list or one

The whole collection, or one specific member of it. Those get two different addresses.

The mental switch

Beginners design APIs as lists of actions: /getUser, /createUser, /deleteUser. REST asks you to think in things instead: there is one /users, and the method decides what happens to it. Fewer addresses, more predictability.

Rules for good endpoints

Nouns, not verbs

/users — the method already says what you are doing.

Plural for collections

/products, not /product. Consistency beats grammar arguments.

Ids identify, they do not describe

/users/10, not /users?getId=10.

Query strings for filtering only

/products?category=books&page=2 narrows a list; it never selects one item.

Nest only one level

/users/10/orders is fine. Four levels deep becomes unreadable.

Lowercase, hyphens if needed

/order-items, not /OrderItems.

Endpoints that give it away

/getAllUsers

The verb is in the URL. The method should carry it.

/users/delete/10

An action in the path. Use DELETE /users/10.

/api/v1/createNewUserAccount

Verb, adjective and noun mashed together. Use POST /users.

/user?id=10&action=update

Everything in the query string, method ignored entirely.

the test

If you can read the URL out loud and it sounds like a command, it is probably wrong. It should sound like a place.

2xx — it worked

The request was understood and carried out. Which 2xx you pick tells the client what kind of success it was.

4xx — the caller's fault

The server is fine; the request was not. Retrying the identical request will fail identically until the caller changes something.

5xx — the server's fault

The request was reasonable and the server broke anyway. Retrying later may well work, because nothing was wrong with what you sent.

The mistake that looks harmless

Returning 200 OK with a body that says { "error": "not found" }. Every tool, cache, monitor and retry rule in the world will treat that as a success. The status code is not decoration — it is the machine-readable part of the answer.

Why REST is like following common rules

Walk into a restaurant in a city you have never visited and you already know how it works: sit, read a menu, order, wait, receive, pay. Nobody taught you that restaurant. Over-fetching and under-fetching

The two problems appear together in almost every real screen.

Over-fetching

An endpoint returns a fixed shape, so you get every field whether you need it or not. Asking for a user's name may deliver twenty other fields with it — wasted bytes on every request, and slower on a poor connection.

Under-fetching

The opposite, in the same screen. One endpoint does not have everything you need, so you must call another, and another. Each call is a full round trip.

Multiple requests

Because resources are separate, a rich screen means many calls. Ten sequential calls at 200 ms of travel each is two seconds of waiting with almost no computing in it.

Versioning

Old apps keep calling your old shapes for years, so you cannot simply change a response. Teams end up with /v1/ and /v2/ living side by side, maintained in parallel.

Network overhead

Every request re-sends headers, cookies and authentication, because REST is stateless and each message must stand alone. That independence is a strength for scaling and a cost on every single call.

Why this matters for the next lesson

Keep the two counters above in your head. A technology exists specifically to let the client ask for exactly the fields it wants in a single request — and that is what lesson 7 is about.

16un-learn these now

Common beginner mistakes

Six confusions that sound reasonable and will cost you an interview.

myth 01

"REST means HTTP."

Correction: HTTP is a protocol — the actual rules for sending a message over a network. REST is a design style for how to arrange your API. REST happens to be almost always built on HTTP because HTTP already has methods, status codes and caching built in. But you can use HTTP without following REST at all, and most badly designed APIs do exactly that.

HTTP

the protocol — how bytes travel and what a message looks like

REST

the style — how you decide to arrange your URLs, methods and responses

myth 02

"REST means API."

Correction: an API is any published way for one program to ask another for something. REST is one particular way of designing one. Every REST API is an API; most APIs in history were not RESTful. Saying "we built a REST" is like saying "we built a Georgian" instead of "we built a house in the Georgian style".

myth 03

"Just use POST for everything."

Correction: it appears to work, and it silently destroys four things. Caches cannot store a POST, so nothing is ever reused. Browsers and tools will not safely retry it. Nobody reading your logs can tell a read from a delete. And a client cannot know whether calling twice is dangerous. The method is not a formality — it is a promise about what the call does.

no caching

every call hits the server

no safe retry

tools dare not repeat it

unreadable logs

every line looks the same

no guarantees

callers cannot reason about it

myth 04

"The HTTP method does not really matter."

Correction: the method is the only part of a REST request that says what you intend to do. Put the verb in the URL instead and you have thrown away caching, safe retries, and the ability of any tool anywhere to understand your API without reading your documentation. GET /deleteUser/10 is a genuine disaster: a search engine crawling your site will delete your users.

myth 05

"Status codes are decoration."

Correction: the status code is the machine-readable part of the answer. Returning 200 OK with an error message inside means every cache stores your error, every monitor reports success, and every automatic retry never happens. Humans read the body; machines read the number, and there are far more machines.

myth 06

"If it returns JSON, it is RESTful."

Correction: JSON is just a text format and appears nowhere in the six principles. An API with a single endpoint called /doThing that accepts POST for every operation and always returns 200 is not RESTful, no matter how much beautiful JSON it produces. REST is about the arrangement, not the format.

21one page

Cheat sheet

Two minutes of revision before an interview or the next lesson.

rest

An architectural style — a set of agreed design rules for APIs built on the web. Not a language, library or protocol.

the name

Representational (you get a description, not the thing) · State (the data) · Transfer (moved over the network).

origin

Named by Roy Fielding in 2000, describing why the web already scaled. Borrowed, not invented.

6 principles

Client–server · stateless · uniform interface · cacheable · layered system · code on demand (optional).

resource

A thing, named with a noun, reachable at a URL. Collections are plural.

architecture

Client → HTTP request → REST API → business logic → database → HTTP response.

GET

Read. No body. Safe, repeatable, cacheable. Must never change anything.

POST

Create. Has a body. Not safe to repeat — calling twice creates two things.

PUT

Replace the whole thing. Fields you omit are wiped. Repeating is harmless.

PATCH

Change only the fields you send. Everything else is left alone.

DELETE

Remove it. Repeating is harmless — it is already gone.

good urls

Nouns, plural collections, ids to identify, query strings only to filter, nest one level, lowercase.

2xx

200 OK · 201 Created · 204 No Content.

4xx

400 bad shape · 401 not logged in · 403 not allowed · 404 not found.

5xx

500 the server broke. Nothing was wrong with your request.

weaknesses

Over-fetching · under-fetching · many round trips · versioning · repeated header overhead.

biggest trap

REST is not HTTP, is not "any API", and JSON alone does not make it RESTful.

23all of it, briefly

Summary

REST is a style, not a thing

A set of agreed design rules for APIs on the web. Nothing to install. Follow the rules and your API is RESTful; break one and it is not.

The name is a description

You receive a representation of the state of a thing, transferred over the network. Three plain words hiding behind an acronym.

Six principles

Client–server, stateless, uniform interface, cacheable, layered system, and code on demand — the last one optional and rarely used.

Nouns in the URL, verbs in the method

Two addresses cover a whole resource: the collection and one member. The method decides what happens to it.

The status code is not decoration

It is the machine-readable part of the answer. Caches, monitors and retry logic all read the number and never read your message.

It has real weaknesses

Fixed response shapes cause over-fetching and under-fetching, so a rich screen means many round trips. Every later alternative exists because of this.

♦memory tricks

Nouns in the road, verbs on the truck

The URL is a place. The method is what you came to do there.

A photo is not the house

Representational: you are always handed a description, never the thing itself.

Every letter arrives alone

Stateless: each request carries its own identification, because the server remembers nothing.

PUT paints the whole wall, PATCH touches up a patch

The words themselves tell you which one wipes the fields you left out.

2 fine · 4 yours · 5 mine

The first digit of the status code already assigns the blame.

Any restaurant, same procedure

The value of a standard is that your knowledge transfers to a place you have never been.

keythree takeaways to keep

one

REST is predictability. Its value is not that any single rule is clever, but that everybody follows the same ones — so learning one REST API partly teaches you all of them.

two

The method and the URL divide the work: the URL names a thing, the method names an action. Every badly designed API you will ever see has broken this one rule.

three

Statelessness is what makes REST scale, and it is also what makes it chatty. Nearly every trade-off in REST comes back to that single decision.
