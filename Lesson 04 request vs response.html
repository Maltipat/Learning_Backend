03the message going out

What is a request?

Start with the everyday meaning. To request something is to ask for it. In computing the word means exactly that, with one extra detail: the asking is written down.

A request is a short, written message that one computer sends to another to ask for something.

It is text not magic

A request is a few hundred characters. You could type one out by hand. Section 7 shows a real one.

It is complete self-contained

It carries everything the server needs: what you want, who you are, and any data you are sending.

It is one-way then it waits

Sending a request does not get you an answer. It gets you a wait.

Who creates it, and when?

Created by: the client

The browser or the app writes it. Not you, and not the server. You tap; the client composes the message.

Sent when: something is needed

You tap a button, open a screen, scroll to the bottom of a list, or the app quietly refreshes in the background.

Sent to: one exact address

The client must already know where to send it. A request with nowhere to go is not a request.

Sent how often: constantly

Opening one ordinary web page can send fifty or more — one for the page, and one for every image, font and script on it.

Why is a request needed at all?

The server cannot guess

It serves thousands of people. It has no idea which one of them you are or what you want until you say so.

It must be written to travel

Two computers cannot share thoughts. Anything crossing a network has to be turned into characters first.

It is the only way in

A server accepts requests and nothing else. There is no side door.

Memory hook

A request is an order slip. Written down, handed over, and then you wait.

04the message coming back

What is a response?

A response is the reply. Also written down, also just text — and it always arrives, even when the news is bad.

A response is the written reply a server sends back, containing an outcome and usually some data.

Created by the server

The server writes it after doing the work. The client never writes its own response.

Always has an outcome a number

Every response starts with a status code saying how it went. Section 8 decodes them.

Usually has data the body

The actual content: your feed, your profile, the search results. Sometimes there is no body at all.

Arrives on the same line the way back

It returns down the exact connection the request opened. No new call is made.

Why does a response exist?

To close the loop

The client is waiting and has stopped moving forward. Without a reply it waits forever.

To report the outcome

Did it work? Were you allowed? Did the server break? Only the server knows, so only the server can say.

To deliver the data

The client has no copy of anything. Whatever it draws on screen, it was handed.

To carry instructions

Responses also say things like "cache this for an hour" or "here is a cookie, send it back next time".

What happens once it reaches the client?

1 · Check the outcome

The client reads the status number first. Good news and bad news take different paths from here.

2 · Unpack the body

The text is turned back into something the program can work with — a list of items, a user, a video chunk.

3 · Update what is on screen

Loading spinner off. Real content on. This is the only moment you actually notice.

4 · Store anything useful

Cookies, tokens and cached copies get kept for the next request.

Memory hook

The response is the plate arriving — with a note on the side saying how the order went.

Why do we need both?

Try running the world with one of the two messages missing. Both broken worlds fail — but they fail in completely different ways, and the difference is worth feeling.

Press the button to run the app in this configuration.

no requests

Nothing ever starts

The server sits perfectly ready and is never asked anything. Your screen shows whatever was already there and never changes again. Silence, forever.

A world with no questions has no answers either.

no responses

Everything starts and nothing finishes

Requests fly out constantly. The client waits, and waits. Every screen is a loading spinner that never stops. This is worse than silence, because it looks like it is working.

This is exactly what a timeout feels like.

both

A closed loop

A question with an answer. The client can stop waiting, decide what to draw, and move on. Two messages is the minimum for anything useful to happen.

The pairing rule

Requests and responses come in pairs. One request gets exactly one response — and if the response is lost, the client cannot tell the difference between "it failed" and "it worked but the answer went missing". That single ambiguity causes more real-world bugs than almost anything else in backend work.

method

The verb. It tells the server what kind of action you want.

in plain words

"I want to send you something new."

if it were missing

The server would not know whether you were reading or writing, and would refuse the message.

The four methods you will meet first

GET read something. POST create something. PUT replace something. DELETE remove something.

A GET should never change anything. That is a promise, not a suggestion.

Address versus question

The URL says which thing. The query says which version of it. /products is the shelf; ?q=laptop&page=2 narrows it down.

Why cookies ride along

Each request arrives with no memory of the last one. The cookie is the client re-introducing itself every single time.

The line that trips everyone up

A 404 is a perfectly successful response. The message travelled, arrived and was read — it simply says the thing you asked for is not there. "The response arrived" and "the request succeeded" are two completely different statements.

12un-learn these now

Common beginner mistakes

Six beliefs that feel right and cause real confusion later.

myth 01

"A request means the internet."

Correction: the request is the message. The internet is the road it travels on. Two different things, and you can have one without the other — a program on your laptop can send a request to another program on the same laptop, never touching the internet at all. Developers do this every day while building.

The message

the request — text, written by the client

The road

the network — carries it, reads nothing

The destination

the server — waiting at a port

myth 02

"If a response came back, it worked."

Correction: a response arriving only proves the conversation completed. The status code says whether it succeeded. A 403 arrived perfectly and means "no". A 500 arrived perfectly and means "I broke". Beginners write code that treats every reply as good news, and then wonder why an error message appears as if it were data.

myth 03

"The request goes straight to the database."

Correction: it does not, and if it ever could, every app would be robbed within a day. The request stops at the server. The server decides whether the request is legitimate, then the server asks the database a question of its own — often a different question from the one you asked.

Clientasks
Serverchecks first
Databaseonly via the server
myth 04

"A response only contains data."

Correction: a response carries three things: an outcome, instructions, and possibly data. The instructions matter more than beginners expect — "keep a copy of this for an hour", "here is a cookie, send it back next time", "the thing you wanted has moved, go here instead". Some responses have no data at all and are still completely useful.

myth 05

"One click means one request."

Correction: opening one ordinary web page fires dozens — one for the page itself, then one each for every image, font, stylesheet and script. A single screen in an app might make five or six separate calls to different addresses. Counting round trips is one of the first real performance skills you will learn.

myth 06

"No response means the request failed."

Correction: silence tells you nothing about what happened at the other end. Your request may have arrived, been processed, and had its reply lost on the way home. This is why pressing "pay" twice can charge you twice, and why serious systems are built so that repeating a request is harmless.

what the user sees

Nothing yet

Each mode fails at a different point, and the user experience is different every time.

not run
Slow responses

Nothing is broken — the answer is simply late. The user stares at a spinner, decides the app is bad, and presses the button again, which sends a second request while the first is still in flight.

Timeouts

The client refuses to wait forever, so after a set period it gives up and reports failure. Crucially, giving up does not cancel the work — the server may finish the job long after the client stopped listening.

Server failures

A 500 means the server broke while trying. The response arrived correctly; the work did not happen. Retrying might work — or might repeat whatever caused the break.

Network failures

The request never leaves, or the reply never returns. From the client's side these two look identical, which is exactly why the ambiguity is dangerous.

The duplicate problem

Because silence is ambiguous, clients retry. A retried "create order" must not create two orders. The fix is to make repeating a request harmless — and that idea will come back in every lesson about writing data.

19one page

Cheat sheet

Two minutes of revision before an interview or the next lesson.

request

A written message a client sends to ask for something. Text, self-contained, one-way.

response

The written reply a server sends back. Always carries an outcome, usually carries data.

who writes what

The client writes the request. The server writes the response. Never the other way round.

request parts

Method, URL, query parameters, headers, cookies, body.

response parts

Status code, headers, body.

method

GET read · POST create · PUT replace · DELETE remove. A GET must change nothing.

url vs query

The URL says which thing. The query narrows it down: ?q=laptop&page=2.

2xx

It worked. 200 OK, 201 Created, 204 No Content.

3xx

Look elsewhere. 301 Moved, 304 Not Modified.

4xx

Your side got it wrong. 400 bad shape, 401 not logged in, 403 not allowed, 404 not found, 429 too many.

5xx

The server's side broke. 500 crashed, 503 unavailable.

json

An agreed way of writing data as text so both sides read it identically.

the pairing rule

One request, one response. Every request is either answered, refused, or lost.

the big trap

"A response arrived" and "the request succeeded" are different statements. Read the status code.

the dangerous silence

No response tells you nothing. It may have worked and lost the reply — so retries must be harmless.

21all of it, briefly

Summary

The request goes out

Written by the client, as text. Carries a method, a URL, query parameters, headers, cookies and sometimes a body. Then the client waits.

The response comes back

Written by the server. Always a status code, usually headers and a body. It returns down the same connection the request opened.

The server is the gate

A request never reaches the database directly. It stops at the server, which decides whether the request is legitimate and then asks its own question of storage.

Read the number first

2xx worked, 3xx look elsewhere, 4xx your mistake, 5xx the server's mistake. Arriving is not the same as succeeding.

One click, many messages

A single screen can fire dozens of pairs. Counting them is how you understand why something feels slow.

Silence is ambiguous

No answer does not mean no work. The request may have succeeded and lost its reply — which is why repeating a request must be safe.
