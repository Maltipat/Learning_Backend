APIs

(Application  Programming  Interface s)

Two programs that have never met, written by different people, in different languages, on different computers — and yet they exchange exactly the right information, in under a second, millions of times a day. This lesson is about the opening in the wall that makes that possible.

03From absolute zero

What is an API?

Forget the three letters for a moment. Start with something you have done a hundred times: you walked up to a counter, said what you wanted, and a few moments later somebody handed it to you over the top of the counter. You never went behind it. That counter is an API.

First, the three words

A P I is short for three words. Most people learn the letters and never learn the words, which is why APIs stay confusing. Take one card at a time.

A · Application

Any program that does a job

Instagram on your phone is an application. The Instagram program running in a data centre is also an application. Two separate programs, two separate computers.

So an API always sits between at least two programs.

P · Programming

Made for programs, not for people

A website is a face for humans: colours, buttons, pictures. An API has no face. What comes out of it is plain text that a program can read — no buttons, nothing to click.

So an API is a machine-to-machine door, not a human one.

I · Interface

A meeting point that keeps two things separate

A plug socket is an interface: it lets you use the power station without ever touching a power station. An interface is the only agreed place two things touch.

So an API is a doorway with rules, not an open room.

The definition, in plain English

An API is a fixed set of requests that one program agrees to accept from other programs — and a promise about exactly what it will send back.

Two halves, and both matter. A list of things you are allowed to ask for. And a promise about the shape of the answer. Nothing about what happens in between. That part is deliberately none of your business.

💡
Say it out loud once: an API is not a thing you can look at. It is an agreement — the same way a menu is not food. The menu tells you what you may order and what will arrive. The kitchen is somewhere else entirely.

Why can't two applications just talk directly?

This is the question that unlocks everything. Four reasons, and they are all practical — not academic.

1 · They are on different computers

Your phone app and the Instagram program are not in the same building, let alone the same memory. One program cannot reach into another computer's memory and take a value out of it. The only way across is a message sent over a network.

A message needs an agreed address and an agreed shape. That agreement is the API.

2 · They are written in different languages

Your iPhone app might be Swift. The backend might be Java. The Android app is Kotlin. A Java object means nothing to Swift. So both sides agree to speak a neutral text format instead — usually JSON.

JSON is just text: {"name":"Aisha","age":24}. Every language can read it.

3 · Direct access would be a disaster

If your phone could talk straight to Instagram's database, it could ask for every row — every private message of every user. The API only offers the five openings. Everything else is unreachable, because there is no opening for it.

Fewer doors is not a limitation. It is the entire security model.

4 · Everything would break, constantly

Suppose 400 million phone apps knew the exact internal layout of Instagram's data. Rename one column and all 400 million break at once — and you cannot update the app in someone's pocket instantly.

The API is a promise you can keep while changing everything behind it.

⭐
Interview tip. When asked "what is an API?", do not say "it connects frontend and backend" — every candidate says that. Say: "It's a contract. It defines what a client may ask for and the shape of the answer, so that the two sides can be built, changed and deployed independently." That sentence is the difference between memorising and understanding.

The three problems APIs actually solve

Problem 1

The language problem

Without: a Swift app and a Java server have no shared way to describe "a user".

With: both sides agree on plain text. The server sends {"id":42,"name":"Aisha"} and every language on earth can read it.

Problem 2

The trust problem

Without: anything that can reach the data can take all of it.

With: the only way in is through a named opening that checks who you are first, and returns your rows only.

Problem 3

The change problem

Without: every internal change is a public change.

With: the opening stays the same shape while everything behind it is rebuilt. Nobody outside notices.

And the reason companies love them: write once, serve everything

Netflix does not have five separate systems for five kinds of screen. It has one API, and five very different clients walk up to the same counter.

Five clients. One set of rules. Build the logic once, fix a bug once, and every screen everywhere is fixed at the same instant.

You tap the words "My orders". At this instant nothing technical has happened at all — there is only a human who wants something.

Frontend builds the request

The app code catches your tap and assembles a message: the address to send to, the action, who you are, and any extra details. The frontend is the one that creates the request.

3
API request travels over the internet

The message leaves your phone as plain text, hops across cell towers and cables, and arrives at the server's address. This is the only thing that crosses the wall.

4
Backend receives it routing

The server reads the address in the message and decides which piece of its own code should handle it. This matching step is called routing.

5
Business logic runs the rules

Is this token real? Has it expired? Is this person allowed to see these orders? Which orders count as "mine"? These rules are the actual product — and they live only here.

6
Database read fetch the rows

The backend asks the database for the matching rows. Notice: your phone never spoke to the database. It asked the backend, and the backend asked the database.

7
Backend shapes the answer build response

Raw rows are not what the app wants. The backend picks the useful fields, drops the internal ones, formats dates, and writes it all as JSON text.

8
API response travels back over the internet

Back it goes: a status code saying how it went, a few headers describing the message, and the body of data. Same road, opposite direction.

9
Frontend receives it render

The app reads the JSON text, turns it into things it can display, and paints rows on the screen. If the status said "failed", it shows a message instead.

10
User sees the result done

Your orders appear. Total time: roughly 180–400 milliseconds — about as long as a single blink.

11Introduction only

Common types of API

APIs are not sorted by how they are built — that comes later. They are sorted by who is allowed to walk up to the counter. Four audiences, four names.

Open to everyone

Public API

Anyone may use it. You sign up, you get a key, you start calling. Usually there is a free tier and paid tiers above it.

Weather data · maps · currency rates · public transport timings

By agreement only

Partner API

Not open to the public. Two companies sign a contract, and only then are keys issued. Access can be revoked when the contract ends.

A travel site reading an airline's live seat availability

Company's own apps

Private API

Built by a company for its own products. Your banking app talks to one right now — but there is no sign-up page for you or anyone else.

The API behind a bank's mobile app or a shop's checkout

Service to service

Internal API

Never leaves the company's own network. One of their programs calls another — say, the orders service asking the inventory service to reserve stock.

Orders → inventory · billing → email · search → catalogue

⭐
An honest note about the vocabulary. In real workplaces "private" and "internal" get used for each other all the time, and nobody will correct you. The distinction worth holding on to is the one that matters in practice: can a stranger call this, and what happens if they try? Everything else is naming.
12Flip each card

Common beginner mistakes

Six sentences that sound reasonable and are wrong. Click a card to see why. If you can explain all six, you understand APIs better than most people who claim to.

Myth 01

"An API is a database."

It gives me data, so it must be where the data lives.

click to flip →
Why it's wrong

An API owns nothing. It is a doorway. Behind that doorway there might be a database — or a file, or a live sensor, or another company's API, or a number calculated on the spot. Same doorway either way. Swap the database for a spreadsheet and the API can look identical from outside.

Myth 02

"An API stores data."

I sent it my photo, so the API is keeping my photo.

click to flip →
Why it's wrong

The API carried your photo and handed it to backend code, which decided where to put it. When the request finishes, the API remembers nothing. It has no memory between calls — which is exactly why the server makes you prove who you are on every single request.

Myth 03

"An API is a programming language."

People say "learn APIs" like they say "learn Python".

click to flip →
Why it's wrong

You cannot write a program in "API". An API is an agreement, and any language can use it or offer it. The same weather API can be called from Python, Java, JavaScript, Go, Swift or a shell command — and it cannot tell which one you used.

Myth 04

"The frontend talks straight to the database."

The screen shows rows, so it must be reading the table.

click to flip →
Why it's wrong

It never does, and it must not. Code on your device can be read and edited by whoever holds the device — so anything it could reach, an attacker could reach too. The frontend asks the backend; only the backend holds the database password, and only it decides which rows are yours.

Myth 05

"An API is just a URL."

You gave me a link — that's the API, right?

click to flip →
Why it's wrong

A URL is one address within an API. The API is the whole agreement: every address, plus which methods each accepts, what must be in the headers, the shape of the body, and every status code it can return. The URL is the doorknob; the API is the door, the frame, the lock and the rules of entry.

Myth 06

"APIs are only for websites."

It is a web thing. Browsers, links, internet.

click to flip →
Why it's wrong

The idea is far older and far wider. Your operating system offers an API so programs can open files. A payment terminal offers one to the card machine. A car's music system offers one to your phone. Web APIs are one popular family, not the whole idea.

13Why the whole industry runs on them

Advantages

Eight reasons, and notice how many of them are about people and time rather than technology.

Separation

Frontend and backend can be built by different people who never speak, as long as both keep the agreement.

Reuse

One API serves the website, both phone apps, the TV app and partners. The rules are written once.

Security

A single narrow entrance is something you can guard, log and rate-limit. A hundred doors is not.

Free to change

Rewrite the whole backend, switch database, move country — as long as the openings keep their shape, nobody outside notices.

Ship faster

Need maps, payments, texts, email? Call somebody's API instead of spending two years building it.

Scale

Because requests arrive at one known place, you can put ten copies of the backend behind it and share the load.

Testable

An agreement can be checked automatically. You can test the backend with no app, and the app against a fake backend.

A business

Some companies sell nothing but API calls — maps, payments, messaging. The API is the product.

14The honest list

Limitations

Every API call is a message to another computer, and that fact carries five permanent costs. Good engineers do not pretend these away — they design for them.

Limitation 1

Network dependency

No network, no API, no app. A function call inside one program cannot fail because of a tunnel; an API call can.

What engineers do: cache the last answer, queue actions, design a real offline mode.

Limitation 2

Latency

Distance costs time. Calling a function in your own program takes nanoseconds; calling an API across a continent takes tens or hundreds of milliseconds. Ten calls in a row is a slow screen.

What engineers do: fewer, bigger calls · servers closer to users · caching.

Limitation 3

Failures you did not cause

The other side can be down, overloaded, or rate-limiting you. Worse, it can accept your request and die before answering — so you genuinely do not know whether it happened.

What engineers do: timeouts, retries, and making repeats safe to send twice.

Limitation 4

Versioning

Once other people depend on your promise, you cannot change it freely. Rename one field and every app still running the old code breaks — including the ones on phones you cannot update.

What engineers do: /v1 and /v2 side by side, add fields instead of renaming them, announce removals long in advance.

Limitation 5

Security

An API is a door you deliberately left open to the whole internet. Everyone will find it: automated scanners within hours of launch.

What engineers do: authentication on every call, permission checks per row, rate limits, validate every field, log everything.

Summary

If you keep only one sentence

An API is the counter: a fixed set of things you may ask for, and a promise about what comes back — so that the two sides never have to know how the other one works.

Memory tricks

A · P · I

Application — a program.
Programming — for programs, not people.
Interface — the only place they touch.

The waiter test

Ask yourself: "is this the waiter, or the kitchen?" The waiter carries and knows the menu. The kitchen decides and cooks. If something is cooking, it is not the API.

देखो · बनाओ · बदलो · हटाओ

The four methods in order: GET dekho (look), POST banao (make), PUT badlo (change), DELETE hatao (remove).

Key takeaways

01 · Two programs cannot touch

Different computers, different languages, no shared memory. A message over a network is the only route, and the API is the agreed shape of that message.

02 · The frontend always asks

The frontend builds and sends the request. It never decides. Passwords, prices, permissions — all decided on the other side of the wall.

03 · The API owns nothing

No storage, no memory between calls. It carries a question in and an answer out. That is the whole job.

04 · A contract is what makes change possible

Because the openings keep their shape, everything behind them can be replaced. That freedom is the real reason APIs exist.
