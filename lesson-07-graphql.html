03the name, decoded

What is GraphQL?

Two words to define first, because both halves of the name are doing real work.

Query language the "QL"

A small written language whose only job is asking for data. You write a short piece of text describing what you want, and send it. That text is the query.

Graph the "Graph"

A graph is things connected to other things. A user has orders; an order has products; a product has reviews. Your data is already a web of connections, and GraphQL lets you walk it in one request.

So, plainly

GraphQL is a language for asking a server for exactly the data you want, plus the software on the server that understands those requests and answers them.

One endpoint

Not dozens of addresses. Almost always a single one, usually /graphql. Everything goes there.

You choose the fields

The response contains the fields you asked for and no others. Ask for a name, receive a name.

Follow connections

A user, their orders and each order's products — in one request, in one reply, in one round trip.

why it matters

The problem it was built for

A news feed is deeply connected

A post has an author, the author has a photo, the post has comments, each comment has its own author. Rendering one screen touches five or six kinds of thing.

REST made that many requests

One endpoint per kind of thing means one round trip per kind of thing — sometimes one per item in a list.

Mobile networks were slow

On a 2012 phone connection, each round trip could cost hundreds of milliseconds. Ten of them is a screen that visibly crawls.

And each reply was too big

Fixed response shapes sent fields the app did not display, over a connection where every byte cost time.

Why developers use it

The client stops waiting for the backend

A new screen needs three extra fields? Change the query. No new endpoint, no backend release, no waiting for another team.

One request instead of five

Fewer round trips is the single biggest win on a slow or distant connection.

The schema is the documentation

The server publishes every type and field it has. Tools read that and offer autocomplete — the API describes itself.

Strong typing catches mistakes early

Ask for a field that does not exist and the server rejects the query before running anything. In REST you would find out from an empty screen.

What GraphQL is not

Not a database. Not a replacement for your backend. Not automatically faster. Not a reason to delete your REST API. Section 16 takes each of those apart properly, because all four are extremely common beliefs.

Over-fetching

You receive fields you never use, because the endpoint returns a fixed shape decided by the server. Asking for one name delivers eighteen fields.

Cost: wasted bytes on every single call, worst on the slowest connections.

Under-fetching

The same endpoint does not have everything the screen needs, so you call another, then another. The opposite problem, in the same screen.

Cost: one extra round trip for every missing piece.

Multiple round trips

Because the calls depend on each other — you cannot ask for order totals until you know the order ids — they must happen in sequence, not in parallel.

Cost: the travel time adds up even when every server responds instantly.

The single root cause

All three are the same problem wearing different clothes: in REST the server decides the shape of the response, so it must guess what every client will need. It guesses too much for one screen and too little for another — often on the same endpoint, on the same day.

Why only the requested fields come back

1 · The server has no fixed response

There is no "the user response" waiting to be sent. The reply is built fresh for each query, from the list of fields in that query.

2 · Every field has its own small function

The server holds one tiny function per field, called a resolver. It runs the resolvers for the fields you named, and only those.

3 · Fields you skip are never computed

Not fetched and thrown away — never fetched at all. If nobody asked for a profile photo, the photo lookup does not happen.

4 · The answer is assembled to match

The results are placed into the same nested shape as your query, and sent back.

What this changes, and what it does not

Changes: who decides the shape

The client now decides. That is the whole invention. Everything else follows.

Changes: how many round trips

Connected data arrives together, so one query replaces a chain of dependent calls.

Does not change: the work still happens

Somebody still queries a database. GraphQL moves the choosing, not the working.

Does not change: your backend

Your rules, your database and your business logic are untouched. GraphQL sits in front of them.

keep this honest

Fewer bytes on the wire does not automatically mean faster. Section 15 shows how a single badly written query can be far more expensive than five REST calls.

choose rest

When REST is the right answer

Simple data with few connections. A public API used by strangers. Anything that benefits from free HTTP caching. File uploads and downloads. A small team without time to learn new tooling.

choose graphql

When GraphQL is the right answer

Deeply connected data. Mobile apps on poor connections. Many different clients wanting different fields from the same data. Fast-moving frontend teams who would otherwise wait on backend releases.

very common

Or both, in the same company

This is what most large companies actually do. GraphQL for the app screens, REST for webhooks, file transfer, machine-to-machine calls and anything a partner consumes. It is not a competition you have to pick a side in.

The habit that matters

—

Mutations always return something

This is the habit REST does not teach you. A mutation is not only an instruction — it is also a query. You say what to change and which fields you want back afterwards.

So one round trip both writes the data and gives you the fresh values to redraw the screen with. In REST that is often a POST followed by a GET.

remember

The braces after a mutation are not decoration. They are you choosing what the server should hand back once the change is done.

Two things beginners get wrong

Using a query to change data

Nothing physically stops you writing a resolver that deletes something inside a query. It is legal and it is a serious mistake — tools, caches and other developers all assume a query is safe to repeat. The keyword is a promise, exactly like GET in REST.

Expecting the HTTP status to tell you

A GraphQL error usually arrives inside a 200 OK, in an errors field beside the data. If your code only checks the status number, it will treat failures as successes.

Limitations of GraphQL

Query complexity

The client writes the query, so the client decides how much work the server does. That is the security problem in one sentence.

Complex caching

REST gets caching free: a GET /products/12 has a unique address, so every browser, proxy and network cache can store the answer without being told anything. GraphQL sends everything to one address, usually by POST, and every query is a different shape — so none of that machinery applies. You must build caching yourself, in the client and on the server, and it is genuinely hard.

Learning curve

REST needs HTTP, which you already knew. GraphQL adds a query language, a schema language, resolvers, and usually a client library to manage caching. A small team can lose weeks to tooling before shipping anything the user notices.

Security concerns

You have handed the client a language for describing work you must perform. A single innocent-looking query can ask for a thousand items, each with their comments, each with their authors. Real deployments must limit query depth, limit complexity, and often reject queries that were not written in advance.

Performance risks — the N+1 problem

Ask for 100 users and each of their orders, and a naive server runs one query for the users and then one per user: 101 database queries from a request that looked tiny. This has a standard fix — batching the lookups together — but the problem does not exist in REST, and nobody warns you about it on day one.

Monitoring is harder

In REST, a slow endpoint shows up as a slow URL in your logs. In GraphQL every request is POST /graphql with a status of 200, so your dashboards show one endpoint that is sometimes slow, and you need extra tooling to learn which field was responsible.

The trade in one sentence

GraphQL moves complexity from the client to the server. The frontend gets simpler and more flexible; the backend gets a harder job, a caching problem and a new class of security risk. Whether that is a good trade depends entirely on your situation — which is the mature answer, and the one worth giving in an interview.

16un-learn these now

Common beginner mistakes

Six beliefs that sound reasonable and are wrong. The first four are the ones that come up in interviews.

myth 01

"GraphQL replaces the database."

Correction: GraphQL stores nothing at all. It has no tables, no rows and no disk. It sits in front of whatever you already have and asks it questions on your behalf. Turn your database off and your GraphQL server can answer nothing.

GraphQL

describes and requests data

your backend

decides and calculates

the database

the only thing that stores

myth 02

"GraphQL is a database."

Correction: the name causes this — it contains "QL" like SQL, so people assume it queries storage directly. It does not. A GraphQL query is not run against tables; it is run against a schema, and each field in that schema is backed by a small function that fetches from wherever you like — a database, another API, a file, or three of those at once for different fields of the same object.

myth 03

"GraphQL is faster than REST."

Correction: sometimes, and sometimes dramatically slower. It sends fewer bytes and needs fewer round trips, which wins on a slow mobile connection. But a REST endpoint hitting a cache never touches a server at all, and a badly written GraphQL query can trigger a hundred database lookups. "Faster" depends on the query, the caching, and the network — three things that vary per screen.

GraphQL usually wins

deeply connected screens on slow networks

REST usually wins

simple, repeated, cacheable reads

myth 04

"GraphQL always replaces REST."

Correction: most companies that adopted GraphQL still run REST endpoints alongside it, deliberately. REST remains the better choice for webhooks, file uploads, machine-to-machine calls, and public APIs where strangers benefit from simple cacheable addresses. Treating this as a war you must pick a side in is itself the mistake.

myth 05

"One request means one database query."

Correction: one request means one network round trip, which is a different claim. Behind it, one resolver runs per field per object — so a query for 50 posts and their authors may run 51 lookups unless the server batches them. The client sees a tidy single request; the server may be extremely busy.

myth 06

"If it returned 200, the query worked."

Correction: GraphQL usually answers with 200 OK even when things failed, putting the problems in an errors field next to the data. A response can even be partly successful — some fields filled in, others null with an explanation. Code that only checks the status number will silently treat those failures as good data.

Mini assignment — an e-commerce API

You are designing the GraphQL API for a shop. Four types: Product, User, Order, Review. For each task, choose the operation type and the correct shape.

refthe schema you were designing against

schema.graphql4 types
type Product {
  id: ID!      name: String!   price: Float!
  image: String  rating: Float     stock: Int!
  reviews: [Review!]!
}

type User {
  id: ID!      name: String!   email: String!
  orders: [Order!]!
}

type Order {
  id: ID!      total: Float!   status: String!
  items: [Product!]!   user: User!
}

type Review {
  id: ID!      rating: Int!     text: String
  author: User!   product: Product!
}

The exclamation mark means "this can never be null". [Review!]! means a list that always exists, containing reviews that are never null. You do not need to memorise that — just recognise it when you meet it.

How to judge a design of your own

Count your types, not your operations. A good GraphQL schema has few types with rich connections between them, so new screens need new queries rather than new server code. If you find yourself adding a field called getProductWithReviewsAndAuthor, you have written a REST endpoint inside a GraphQL schema.

21one page

Cheat sheet

Two minutes of revision before an interview or the next lesson.

graphql

A query language for asking a server for exactly the data you want, plus the server software that answers it.

the name

Graph = your data is things connected to things. QL = query language.

origin

Built inside Facebook in 2012 for the mobile news feed; open-sourced in 2015; moved to the GraphQL Foundation in 2018.

the one idea

The client decides the shape of the response. Everything else follows from that.

endpoint

One, usually /graphql, usually POST.

schema

The full published list of every type and field the server offers. It is also the documentation.

type

A kind of thing — Product, User, Order — with a fixed set of fields.

field

One piece of a type. Every field has a resolver behind it.

argument

Extra input to a field: user(id: 10), orders(last: 3).

query

Reads data. Must never change anything — the same promise GET makes in REST.

mutation

Changes data, then returns whichever fields you asked for afterwards.

subscription

Keeps a connection open so the server can push updates as they happen.

resolver

The small function behind a field that actually fetches its value.

shape rule

The response mirrors the query exactly. Predict one from the other.

errors

Usually arrive inside a 200 response, in an errors key. Responses can be partly successful.

graphql wins

Connected data, slow networks, many client types, frontend teams that need to move fast.

rest wins

Simple cacheable reads, public APIs, file transfer, small teams, easy monitoring.

n+1 problem

One query per field per object. 100 users plus their orders can mean 101 lookups unless you batch.

biggest trap

It is not a database, not always faster, and not a replacement for REST.

23all of it, briefly

Summary

The client decides the shape

That single change is the whole invention. GraphQL is a query language plus the server software that understands it — nothing is stored and nothing is replaced.

Query and response mirror each other

The query is the answer with the values removed. Once you see that, you can predict any response without running it.

Resolvers do the actual work

One small function per field. Fields you did not ask for are never computed — that is why the reply contains only what you named.

It beats REST at some things

Fewer round trips, exact data, one endpoint, flexible clients. It loses at caching, simplicity, monitoring and predictable server cost.

The client can now cost you money

You handed out a language for describing work you must perform. Depth limits, complexity limits and batching are not optional extras in production.

It moves complexity, it does not remove it

The frontend gets easier and the backend gets harder. Whether that is worth it depends on your data, your clients and your team.

♦memory tricks

Buffet versus à la carte

REST plates up a fixed selection. GraphQL cooks exactly what you ordered — and needs a better kitchen to do it.

The query is the answer, hollowed out

Delete the values from a GraphQL response and you have rewritten the query.

One door, many rooms

REST gives you a corridor of doors. GraphQL gives you one door and a form to fill in.

Small query, big bill

Bytes sent tell you nothing about work done. Always ask what the resolvers had to do.

Two hundred is not a yes

Read the errors key, not the status code. A GraphQL reply can be half right.

It is a waiter, not a pantry

GraphQL fetches and shapes. It never stores. Nothing lives inside it.

keythree takeaways to keep

one

GraphQL is not a better REST. It is a different division of responsibility: the client describes what it wants, and the server takes on the work of assembling it.

two

Every advantage in this lesson comes from the same sentence, and so does every limitation. Fewer round trips and hard caching are the same fact seen from two sides.

three

The right answer to "REST or GraphQL?" is a question back: how connected is the data, how varied are the clients, and how much do you need caching? Anyone who answers without asking that has not used both.
