Section 02 · warm-up2–3 min

Where you already are

Four ideas you already own. Read them once, then we spend the rest of the lesson on the fifth.

Backend

The part of the app the user never sees. It holds the rules and the data, and it decides what is allowed.

API

A published way in. A fixed set of things you may ask for, so nobody has to touch the backend's insides.

REST API

An API organised around resources. Addresses like /users/42, and HTTP methods for the verbs.

GraphQL

One endpoint plus a query language. You describe the shape of the data you want and get exactly that.

How RPC fits into that family

All three carry the same need across the same network. They differ in what you name when you ask. Watch the same need — "give me user 42's name" — expressed three ways.

Memory aid. REST asks for a चीज़ (thing). GraphQL asks for a शक्ल (shape). RPC asks for a काम (action). Thing, shape, action — that ordering is also roughly the order they were invented.
One honest caveat before we start. RPC is the oldest of the three, not the newest. The idea was written up in the early 1980s, long before REST was named in 2000. What is new is how good it has become at one specific job: machines talking to other machines inside your own company, thousands of times a second.
Section 03 · the idea

What is RPC?

Three words, and every one of them is doing work. Take them one at a time — nothing here needs any prior knowledge.

Word 1

Remote

Not here. On a different computer, or at the very least in a different running program. Between you and it there is a network — a gap you cannot step across.

Opposite of remote: local — inside your own program's memory.

Word 2

Procedure

A named block of code that does one job. You give it inputs, it gives back a result. getUser(42) takes a number and returns a user.

Same thing, four names: procedure · function · method · subroutine.

Word 3

Call

Run it now and wait for the answer. You stop, it works, you continue with whatever it handed back. That pause is the important part.

You have called functions since your first line of code. RPC changes only where the function is.

Put together

RPC lets your program run a function that lives on another computer, using the same syntax you would use for a function in your own file.

That is the entire pitch. The network trip, the packing, the unpacking, the reply — all of it is hidden so that the call reads ordinary.

WHAT ACTUALLY HAPPENS

    Why does RPC exist at all?

    Because programmers already knew how to call functions

    Every developer on earth can read getUser(42). RPC borrows that familiarity instead of inventing a new mental model.

    Because one machine stopped being enough

    Split a big program into services and the pieces land on different machines. They still need to ask each other for work.

    Because the plumbing is always the same

    Packing, sending, unpacking, replying. Identical for every call, so a machine can generate it and no human should hand-write it.

    A dated fact worth knowing. The idea was formalised in a 1984 paper by Andrew Birrell and Bruce Jay Nelson, Implementing Remote Procedure Calls. Sun's version shipped soon after and became the machinery under network file sharing. RPC is older than the web.

      The one thing RPC actually gives you

      You write the function's shape once, in a small file both sides agree on. A generator turns that file into two pieces of code: a look-alike for the caller, and an unpacker for the far side. Neither piece is written by hand, so neither piece can drift out of step.

      1 · You declare the shape

      One small file: this function is called getUser, it takes an id number, it returns a user with a name and an email.

      rpc getUser(GetUserRequest) returns (User);

      2 · A generator writes both stubs

      From that one file it produces the caller's look-alike and the far side's unpacker — in whatever languages each side happens to use.

      // generated, do not edit User getUser(int id) { … }

      3 · You just call it

      Your code contains one line and no plumbing. Add a field to the shared file, regenerate, and both sides move together.

      var u = client.getUser(42);
      The word for that small file is a contract — or, in the tools' own vocabulary, an IDL (interface definition language). It is the single sentence both machines have agreed on. Almost every advantage and every limitation in this lesson traces back to that file existing.

      1

      Your code calls the functionnear room

      The line getUser(42) runs. Your program does exactly what it always does with a function call: it hands over the argument and waits for a return value. At this instant your program does not know, and does not care, that anything unusual is about to happen.

      2

      The client stub catches itthe look-alike

      The function your code reached is not the real one — it is the client stub, a generated look-alike with the same name and the same argument list. Its only job: turn the arguments into a stream of bytes, add the name of the procedure being called and a request id, and hand the bundle to the network layer.

      3

      The bytes cross the gapno code runs here

      The bundle travels as an ordinary network message — typically over TCP, and in modern systems inside an HTTP/2 connection. This is the only stage where nothing is executing. The message is simply in flight, and this is where a call can be lost, delayed, or duplicated.

      4

      The RPC server accepts and the server stub unpacksthe look-alike, again

      A process on the far machine is listening. It reads the bytes, finds the procedure name, and hands the rest to the matching server stub. The stub rebuilds the argument — the number 42 becomes a real number in that machine's memory again — and then calls the real function.

      5

      The real procedure runsbusiness logic

      Now, finally, your actual code executes: check the caller is allowed, validate the id, decide what to fetch. This is ordinary code. It has no idea it was called from another machine, and that is deliberate — the stub kept the network out of it.

      6

      It reads the database, if it needs tooptional

      The function may run a query, may call a cache, may call another service, or may do none of these and just do arithmetic. Nothing about RPC touches the database. The database sits behind the function, exactly as it would for a local call.

      7

      The return value is packed and sent homereply

      The function returns an object. The server stub turns it into bytes, tags it with the same request id it arrived with — so the caller can match reply to call — and sends it back across the gap.

      8

      Your program resumesround trip closed

      The client stub receives the bytes, rebuilds a real object in your memory, and returns it from that original line. Your program continues on the next line holding an ordinary local object. Total elapsed time inside one data centre: often under a millisecond.

      Section 06 · inside the wire

      Internal working: how a 42 becomes bytes and back

      Stage 2 said "turn the arguments into bytes". That sentence hides the single most important mechanism in RPC. Here it is in full, with the real bytes — you can check them by hand.

      Why can't you just send the object? A live object exists at a memory address inside one running program. That address means nothing anywhere else, and the far machine may store numbers in a different byte order, or run a different language entirely. So the object has to be flattened into a sequence of bytes that carries its meaning instead of its location. Flattening is called serialisation. Rebuilding is deserialisation.

      Payload only — real messages also carry framing and headers, which narrows the gap. But the shape of the result holds: binary is smaller, text is readable. That is the whole trade.

      Where the 62 bytes go

      JSON-RPC spends most of its budget on the names of things: "jsonrpc", "method", "params". Every single call re-sends those spellings.

      Where the 2 bytes go

      Protobuf sends 08 2a. The 08 means "field number 1, and it's a plain integer". The 2a is 42 in hexadecimal. The name id is never transmitted — both sides already read it in the contract file.

      The cost of that saving. You cannot read 08 2a in a log, and you cannot debug it with curl. You need the contract file to make sense of the bytes at all.
      Six stages, six words. बुलाओ · पैक करो · भेजो · खोलो · चलाओ · वापस भेजो — call, pack, send, open, run, send back. If you can recite those six in order, you can reconstruct this entire section from memory.

      RPC vs REST vs GraphQL

      Three ways to send a request over the same network. Click any row to see why the row lands the way it does. A ◆ marks a genuine advantage; several rows deliberately have no winner.

       RESTGraphQLRPC
      Communication style You address a thing: /users/42

      		 You describe a shape and post it to one place

      Reach for REST when…

      Strangers will call it, it must be cacheable, or you want anyone to debug it from a terminal.

      Reach for GraphQL when…

      Many different screens need different slices of the same data, and the front-end changes weekly.

      Reach for RPC when…

      Both sides are yours, the traffic is heavy, latency matters, and the operations are genuinely actions.

      They are not rivals in practice. A very common production shape: REST or GraphQL at the edge, where the public and the browsers are — and RPC behind it, between your own services. Choosing one does not forbid the others.

      Section 11 · names you will hear

      Modern RPC systems — introduction only

      Four names, four sentences each. You are not learning how to use these today; you are learning what they are so the words stop being noise. Every one of them implements the same eight stages you stepped through in section 5.

      Google · 2015HTTP/2binary

      gRPC

      The default choice for new internal services today. Contracts are written in Protocol Buffers, messages travel as binary over a long-lived HTTP/2 connection, and it supports streaming — a call can return a flow of messages rather than a single reply.

      Contract file: .proto  ·  Grew out of: Google's internal system, Stubby
      Facebook · 2007Apachepluggable

      Apache Thrift

      Built at Facebook and given to the Apache Foundation. Its distinguishing feature is how pluggable it is: you choose the wire protocol and the transport separately, and it generates stubs for a long list of languages from one contract file.

      Contract file: .thrift  ·  Still common in: older large codebases
      1998XMLhistorical

      XML-RPC

      The ancestor. A call is an XML document posted over HTTP: the method name and the arguments spelled out in tags. Extremely verbose by today's standards, and mostly of historical interest — SOAP grew directly out of it.

      Reads like: <methodName>getUser</methodName>
      2010 · v2.0JSONtiny spec

      JSON-RPC

      The same idea with JSON instead of XML, and a specification short enough to read over a coffee. Still actively used where human-readable calls matter more than raw speed — the Language Server Protocol your editor speaks, and most blockchain node APIs, are JSON-RPC.

      You met its bytes in section 6 — all 62 of them
      Do not confuse the family with one member. gRPC is an RPC system, the way a Labrador is a dog. Saying "we use RPC" tells someone the style of communication; saying "we use gRPC" tells them the tooling, the wire format and the contract language too.

      Section 13 · what you gain

      Advantages

      Each of these follows from something concrete you have already seen — the contract file, the generated stubs, or the binary payload. Nothing here is magic.

      Fast communication

      Small binary payloads, no field names re-sent on every call, and one connection reused for thousands of calls. Inside a data centre a call often completes in well under a millisecond.

      Strong contracts

      The contract file is checked by a compiler, not by hope. Misspell a field and the build fails on your machine — long before anything reaches production.

      Reusable services

      One service publishes one contract, and every team generates its own client from it. Twenty teams, twenty clients, zero duplicated plumbing.

      Built for machine-to-machine traffic

      No browser to please, no URLs for humans to read, no caching layer to satisfy. When both ends are servers, all that ceremony is cost with no benefit.

      A mental model you already have

      New engineers read payments.authorize(orderId) and understand it instantly. There is no URL design debate, and no argument about which HTTP verb an action deserves.

      Language independence

      One contract generates a Java client, a Go server and a Python script. The two sides never need to agree on a language — only on the contract.

      The advantage behind all the others. You stopped hand-writing the plumbing. Everything above is downstream of the fact that a generator, not a person, writes the code that touches the network.
      Section 14 · what it costs

      Limitations

      An engineer who can only list advantages is not yet trustworthy. Every item here is the exact price of an item in the previous section.

      Tight coupling

      The caller knows the callee's function names and argument types. That is a much closer relationship than "we both speak HTTP" — rename a method and every caller must be rebuilt.

      Price of: strong contracts

      Version compatibility

      Two services, two deploy schedules, one shared contract. You must be able to change the contract while old and new code are running at the same time — see the widget below.

      Price of: generated code

      Debugging complexity

      A packet capture shows 08 2a. No browser can call it, curl cannot help, and the stack trace stops at the stub. You need distributed tracing to see the whole story.

      Price of: binary speed

      Network dependency

      A call that reads like a local one still crosses a network that can be slow, lossy or absent. Every remote call needs a timeout, a retry policy and an answer to "what if this never returns?"

      Price of: the illusion itself

      Language and platform gaps

      A generator has to exist for your language, and it has to support the features your contract uses. Browsers in particular cannot speak raw gRPC — they need a proxy in between.

      Price of: binary wire formats

      Easy to expose too much

      Because adding a method is so cheap, internal services accumulate them. Every method is a door, and a door nobody remembers is a door nobody is guarding.

      Price of: low friction

      Change one line of the contract and see who breaks

      Section 15 · unlearning

      Common beginner mistakes

      Six sentences that sound right and are wrong. Click a card to turn it over. If you can explain the back of each one out loud, you understand RPC better than most people who list it on a CV.

      Myth 01"RPC is just another word for REST."

      They both send requests over a network, so surely they are the same family with different branding.

      Click to turn over
      What's trueDifferent unit of thought.

      REST names resources and leans on HTTP's verbs. RPC names actions and often does not use HTTP semantics at all. You can even build RPC over raw TCP, where there is no GET to speak of.

      Myth 02"RPC means gRPC."

      Every article about RPC seems to be about gRPC, so they must be the same thing.

      Click to turn over
      What's trueOne dog, not the species.

      RPC is a style, described in 1984. gRPC is one implementation, released in 2015. Thrift, XML-RPC, JSON-RPC and Java RMI are all RPC too, and none of them is gRPC.

      Myth 03"An RPC call reaches into the database."

      The call goes to the server, the server has a database, so the call reads the database.

      Click to turn over
      What's trueRPC delivers a function call. Full stop.

      What that function then does is entirely its own business. Simulation 3 is a complete RPC service with no database at all — it only multiplies numbers.

      Myth 04"A remote call is a local call that takes longer."

      It is the same syntax and the same result, just slower. Add a timeout and you are done.

      Click to turn over
      What's trueIt fails in ways local calls cannot.

      It can be duplicated, lost after succeeding, or hang forever. A local call has one failure mode: it throws. This exact point is the subject of a famous 1994 paper, A Note on Distributed Computing.

      Myth 05"RPC is always faster than REST."

      It is the one everybody reaches for when performance matters, so it must win by design.

      Click to turn over
      What's trueThe speed comes from the details, not the name.

      Binary encoding, a reused connection and no repeated field names — those are what make it fast. A lean REST service over the same connection can be very close. Measure your own traffic.

      Myth 06"I'll write the stub myself."

      It is only some packing and unpacking. How hard can it be to hand-write it once?

      Click to turn over
      What's trueThen you have re-created section 4.

      A hand-written stub is plumbing that can drift out of step with the other side. The entire value of RPC is that one file generates both halves, so they cannot disagree.

      RPC · one-page revision Lesson 08

      The three words

      • Remote — on another computer or process, across a network
      • Procedure — a named block of code: function, method, subroutine
      • Call — run it now, and wait for what it returns

      The eight stages

      • 1 · your code calls the function
      • 2 · the client stub packs the arguments
      • 3 · bytes cross the gap — no code runs here
      • 4 · the server stub unpacks them
      • 5 · the real procedure runs
      • 6 · it reads a database, or doesn't
      • 7 · the return value is packed and sent home
      • 8 · your program resumes with a local object

      Internal six, in order

      call → serialise → transfer → deserialise → execute → return

      Vocabulary

      • Stub — generated look-alike. Client side also called a proxy, server side a skeleton
      • IDL / contract — the one file both sides agree on
      • Serialisation — object → bytes. Marshalling is the broader word
      • Unary / streaming — one reply, or a flow of them

      Choosing between the three

      • REST — public, cacheable, debuggable in a browser
      • GraphQL — many clients wanting different field sets
      • RPC — your own services, heavy traffic, real actions
      • Common shape: REST or GraphQL at the edge, RPC behind it

      The four systems

      • gRPC — Google, 2015. HTTP/2 + protobuf. Streams
      • Thrift — Facebook → Apache. Pluggable everything
      • XML-RPC — 1998. XML over HTTP. SOAP's ancestor
      • JSON-RPC — tiny spec. Used by LSP and blockchain nodes

      Failure rules

      • Every remote call gets a timeout. No exceptions
      • A lost reply is indistinguishable from a call that never ran
      • Retrying a write needs an idempotency key
      • At-most-once vs at-least-once is a choice you must make on purpose

      Versioning rules

      • Field numbers are the identity, not field names
      • Add optional fields freely — old code ignores them
      • Never reuse a retired field number
      • Never change a field's type in place — add a new field instead

      Key takeaways

      • 01RPC is a style of communication, not a product. gRPC, Thrift, XML-RPC and JSON-RPC are products.
      • 02The stub is the whole trick. Without it there is no illusion and you are back to hand-written plumbing.
      • 03A live object cannot travel. Serialisation turns meaning into bytes; deserialisation turns bytes back into an object.
      • 04RPC delivers a function call. What that function does — database, cache, arithmetic, nothing — is its own business.
      • 05The contract file buys you compile-time safety and costs you tight coupling. That is the central trade.
      • 06A remote call can be lost after succeeding. That single fact is why idempotency keys exist.
      • 07REST, GraphQL and RPC coexist happily: public edge, private interior.
